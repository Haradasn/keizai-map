## 1. 43都道府県の表を、同じ37部門にそろえる

都道府県は、それぞれ自分の県の産業連関表を公表しています。ただし、形式は県ごとに違います。

| 違い | 県の数 | 例 |
|---|---:|---|
| 部門の分け方が全国の37部門と違い、部門名で対応づけた | 12 | 北海道は106部門、長崎県は108部門、広島県は45部門 |
| 39部門の表で、林業と漁業を農業と合わせて「農林漁業」にした | 5 | 兵庫県、福岡県、三重県 など |
| 金額の単位が違う（万円、千円） | 6 | 京都府、佐賀県 など |
| PDF でしか公表していない | 3 | 山形県、山口県、静岡県 |
| 397部門の細かい表から合算した | 1 | 沖縄県 |

これを県ごとにコードで書き分けると、すぐに手に負えなくなります。そこで、**「どのファイルの、どのシートの、何行目からが表か」を設定ファイルに書く**ことにしました。

```json:pref_raw/SOURCES.json（秋田県。注記の欄は省略）
{
  "name": "秋田県", "year": 2020,
  "file": "akita_2020_39.xlsx", "sheet": "取引基本表 ",
  "name_row": 3, "first": 4, "code_col": 0, "name_col": 1,
  "special": "by_name",
  "by_name": { "農業": "01", "林業": "01", "漁業": "01", "電力・ガス・熱供給": "46" },
  "url": "https://www.pref.akita.lg.jp/pages/archive/98381"
}
```

`by_name` は「県の部門名 → 全国の37部門のコード」の対応です。書くのは、全国と名前が違う部門だけです（秋田県なら4つ）。名前が全国と同じ部門は、自動で対応づけます。対応先が決まらない部門が1つでもあれば、ビルドを止めます。

```python:pipeline/pref_build.py（抜粋）
key = to.get(n) or NAT.get(n)          # 設定に書いた対応 → なければ全国と同じ名前
assert key, (slug, "対応先のない部門", n)
```

### 検算その1：1部門ずつ、収支が合うか

読み込んだ表は、部門ごとに2つの式で検算します。

```python:pipeline/pref_build.py（抜粋）
mi = dem + e - X      # 移輸入 = 県内需要 + 移輸出 - 県内生産額（需給の収支から）
assert abs(intin + va - X) <= max(2, X * 1e-6), (slug, n, "費用側", intin + va, X)
assert mi >= -max(2, X * 1e-6), (slug, n, "移輸入が負", mi)
```

- **費用側**：仕入れ（中間投入）＋付加価値＝生産額
- **需給側**：生産額＋移輸入＝県内の需要＋移輸出

列を1つ読み違えたり、単位を間違えたりすると、ここで落ちます。PDF でしか公表していない3県は、PDF から文字を取り出して（`pdftotext -layout`。フォントの埋め込みが壊れている PDF は `pdfplumber`）いったん Excel にし、ほかの県と同じ検算を通しています。数字を1つ読み違えれば、収支が合わなくなるので分かります。

### 検算その2：公表されている「粗い表」を再現できるか

北海道は、最初は38部門の表を使っていました。ところが38部門では「機械」がひとまとめになっていて、全国の37部門（はん用機械、生産用機械、電気機械…）と比べられません。地図で機械の産業を選ぶと、北海道は灰色になっていました。

そこで、106部門の表に切り替えて、名前で37部門に合算し直しました。このとき、合算が正しいことをどう確かめるかが問題です。

答えは単純で、**106部門の表から、公表されている38部門の表を作り直して、全部の数字が一致するか**を見ました。全グループで差は0でした。宮城県（101部門）も同じ方法で確かめています。

「細かい表に切り替えたら、古い粗い表の合計と一致することを確かめる」は、いまは作業メモ（`CLAUDE.md`）に書いてあるルールです。

## 2. 「稼ぎ頭」を特化係数で決めたら、31県で外れていた

![県ページ：県の形と、稼ぎ頭の一文、産業の構成を全国と比べる帯](https://keizai-atlas.com/img/qiita/15_pref.png)

43県がそろったので、「各県の看板産業を1枚の地図にしよう」と考えました。最初の決め方は、こうです。

> 産出額の3%以上を占める産業のうち、**特化係数**がいちばん大きいもの

特化係数は「その県での割合 ÷ 全国での割合」です。全国より偏っている産業が分かるので、地域分析でよく使われます。地図もでき、県ごとの共有画像もでき、公開もしました。

そのあと、サイト全体を見直していて、トップページの問いが気になりました。

> あなたの県は、**何で稼いでいる？**

「稼いでいる」と聞いているのに、答えは「全国と比べて偏っている産業」です。問いと答えが合っていません。「稼ぐ」を素直に読めば、**県の外に売っている額**のはずです。県の産業連関表には、部門ごとの移輸出額（他の都道府県と海外への販売額）が載っています。

2つの決め方で、答えを比べてみました。

| 県 | 特化係数で決めた答え | 県外・海外にいちばん売っている産業 |
|---|---|---|
| 広島県 | 鉄鋼（全国の4.3倍） | 輸送機械（移輸出額の26%） |
| 北海道 | 農林漁業（4.2倍） | 飲食料品（22%） |
| 三重県 | 電子部品（7.8倍） | 輸送機械（17%） |
| 滋賀県 | はん用機械（6.2倍） | 輸送機械（13%） |
| 千葉県 | 石油・石炭製品（4.5倍） | 化学製品（12%） |
| 沖縄県 | 医療・福祉（2.0倍） | 運輸・郵便（27%） |

**43県のうち31県で、答えが違いました。**

理由は、あとから考えれば当たり前です。特化係数は「割合の比」なので、金額の大きさを見ていません。広島県の鉄鋼は全国の4.3倍に集中していますが、外に売っている額は輸送機械（自動車や船）の半分に届きません。沖縄県の医療・福祉は、そもそも県外にほとんど売りません（県の移輸出額の0.5%）。

### 直し方：定義を1つの関数にして、全部そこから作る

「稼ぎ頭」の定義を、移輸出額がいちばん大きい部門に変えました。

```python:scripts/build/build_pref.py（抜粋）
def kasegi_ranking(p, n=4):
    """県外・海外への販売額(移輸出額)が大きい順の部門。[(部門, 県の移輸出額に占める割合)] を n 件。
    「何で稼いでいるか」を、全国平均との比較(特化係数)ではなく、県の外に売っている額で数える。"""
    ranked = sorted((o for o in p["sectors"] if (o.get("exp") or 0) > 0), key=lambda o: -o["exp"])
    return [(o, o["exp"] / p["exp_total"]) for o in ranked[:n]]
```

トップページ、県のページ、稼ぎ頭マップ、共有画像は、すべてこの関数から作ります。同じ数字が4か所に出るので、どこかだけ古い定義のまま残ると、すぐ食い違います。そこで、テストの中でもう一度、データから答えを計算し直して、ページの文と一致するかを見ています。

```python:tests/test_static.py（抜粋）
top = max(p["sectors"], key=lambda o: o["exp"])
share = top["exp"] / p["exp_total"]
page = (S / "prefecture" / f"{slug}.html").read_text(encoding="utf-8")
assert f"稼ぎ頭は<b>{top['n']}</b>" in page, slug
```

直したあとの集計では、稼ぎ頭が輸送機械の県が10、飲食料品が9、商業が5、化学製品と電子部品がそれぞれ4でした。

![43都道府県の稼ぎ頭マップ](https://keizai-atlas.com/share/kasegi-map.png)

### この定義の限界

これは「筆者の定義」で、サイトにもそう書いています。注意点は3つあります。

- **売上の額であって、利益や付加価値ではありません。** 部品を県外から買って組み立てて売る産業は、大きく出ます。
- **「商業」は、卸売・小売の取り分（マージン）です。** 大阪府や兵庫県の稼ぎ頭は商業ですが、売った品物の値段そのものではありません。
- **東京都の「本社」は、東京都の表だけにある部門です。** ほかの県では各産業に含まれている本社の活動を、東京都は独立させて数えています。県どうしでそのまま比べられないので、ページに注記を付けました。

学んだことは、**指標を決める前に、問いを日本語で書いて、答えの文に当てはめてみる**ことです。「広島県は鉄鋼で稼いでいる」と書いた時点で、広島の人なら違和感を持ったはずです。

## 3. 需給バランスの式を、そのまま1枚の図にする

![産業ページ：乗用車がどこから来て、どこへ行くか](https://keizai-atlas.com/img/qiita/12_industry_flow.png)

県のページには「県の形」という顔があります。一方、108産業と37部門のページ（145ページ）は、数字カードと表が並ぶだけでした。産業ごとの顔になる図がほしい。

産業連関表では、どの産業についても、次の2つの式が成り立ちます。

```text
国内生産 ＋ 輸入 ＝ ほかの産業が使う分 ＋ 家計 ＋ 投資 ＋ 政府 ＋ 輸出
国内生産 ＝ ほかの産業からの仕入れ ＋ 付加価値
```

左辺と右辺を、そのまま左右に並べれば図になります。左が「出どころ」、右が「行き先」。帯の太さは金額です。

- 乗用車：出どころの半分以上が自動車部品。行き先の50%は輸出。
- 石炭・原油・天然ガス：出どころの約98%が輸入。行き先の8割は、石油製品と電気。
- 医療：出どころの半分は付加価値（人件費など）。行き先の82%は政府（公的な保険からの給付）。

![石炭・原油・天然ガス：出どころのほとんどが輸入](https://keizai-atlas.com/img/qiita/14_industry_oil.png)

式をそのまま描いているので、推計や仮定は入っていません。そして、**左右の合計が一致するはず**なので、ここにも検算を入れられます。

```python:scripts/build/build_industry.py（抜粋）
# 検証: 出どころの合計と行き先の合計は一致する(産業連関表の需給バランス)
supply = sum(item["value"] for item in left)
demand = sum(item["value"] for item in right)
assert abs(supply - demand) <= 0.002 * total + 0.5, (sid, supply, demand)
```

在庫の取り崩しや、くずの回収は、表ではマイナスの需要として記録されています。右側に負の帯は描けないので、左側（出どころ）に移しました。銑鉄・粗鋼や紙のページで出てきます。

### 図を作ったら、古い表の誤りが見つかった

図の右側の割合を計算していて、既存の表がおかしいことに気づきました。「石炭・原油・天然ガス」の販売先の表に、こう出ていたのです。

| 販売先の産業 | 金額（兆円） | 売上に占める割合 |
|---|---:|---:|
| 石油製品 | 5.7 | **4208.2%** |

販売額を「国内生産額」で割っていたのが原因です。原油はほとんどが輸入なので、国内生産（約1,300億円）で割ると、とんでもない数字になります。分母を「輸入品を含む行き先の合計」に直しました。

もう1つ。乗用車のように、ほかの産業へほとんど売らない産業では、「主な販売先は、主な仕入れ先は…」という途中で切れた文と、中身のない表が出ていました。145ページを1つずつ目で見ることはしていなかったので、気づいていませんでした。

### ラベルの位置は、ビルド時に行数を見積もって決める

帯は SVG ですが、ラベルは HTML にしました。折り返せますし、相手の産業のページへのリンクにできます（供給網をたどって歩けます）。

問題は、細い帯が並ぶとラベルが重なることです。ブラウザで測って直す方法もありますが、静的サイトなので、**ビルド時に「狭い画面で何行になるか」を字数から見積もって**、細い項目にもその行数ぶんの高さを割り当てています。

```python:scripts/build/build_industry.py（抜粋）
def label_lines(label, amount, width_em):
    """ラベル(名前と金額)が、幅 width_em(全角の字数)の欄で何行になるかの見積もり。金額は途中で折り返さない。"""
    name_em = text_em(label)
    lines = max(1, math.ceil(name_em / width_em))
    last_line = name_em - (lines - 1) * width_em
    return lines + (1 if last_line + 0.5 + text_em(amount) > width_em else 0)
```

見積もりなので、外れることがあります。そこで、145ページすべてを幅320〜1280pxで開き、ラベルの四角が重なっていないかを機械的に調べました。項目の多いページは、テストにも入れています。

![全産業の中での位置：細い線が108産業、朱の線がこの産業](https://keizai-atlas.com/img/qiita/13_rulers.png)

数字カードも、やめました。「付加価値率14%」と書かれても、高いのか低いのかが分からないからです。108産業すべてを細い線で並べ、その産業だけ朱で示す「ものさし」にしました。

## 4. 「AIが作った感がすごい」デザインを作り直す

実装の大部分は、今回も AI（Claude）と一緒に進めました。途中で一度、デザインを「近未来な感じに」と頼んだことがあります。出てきたのは、暗い背景に、光る枠とグラデーション、流れる光の粒、という画面でした。

私の返事はこうでした。

> 確かにかっこよくなった。でも、これはAIが作った感がすごいよ。

Claude に原因を考えてもらうと、3つに整理されました。

1. **構成を変えずに、色だけ塗り替えていた。** 中身は「数字カード＋表」のままでした。
2. **どのサイトにも使える部品だった。** 光る枠もグラデーションも、経済のサイトである必要がありません。
3. **データを表さない動きがあった。** 流れる光の粒は、実際の取引とは関係のない飾りでした。

そこで、サイトの名前（Atlas＝地図帳）から決まりを作り直しました。

- 面は**海**、パネルは**紙**、文字と罫線は**墨**、強調は**朱**。
- 光、ぼかし、グラデーション、影、飾りの動きは使わない。
- **動かすのは、データを表すものだけ。**
- 画面の主役は、文章や部品ではなく、データそのものにする（県の形、帯、立体地図の柱）。

3つ目の決まりは、あとで自分たちを縛りました。トップの立体地図は、ゆっくり左右に回っていました。立体感は出ますが、これはデータを表していません。やめて、代わりに**県や産業を選ぶと、柱が前の高さから次の高さへ伸び縮みする**ようにしました。動きを、飾りから操作への返事に移した形です。

### 小ネタ：傾けた地図を、柱の先まで枠に収める

回転をやめると、別の問題が見えました。北海道の柱が、画面の右端で切れていたのです。

地図を枠に合わせるとき、県の輪郭（地面の点）だけを見ていました。ところが、傾けた地図では、柱は真上に伸びません。**カメラの真下の点から放射状に、外側へ傾いて見えます**。端にある背の高い柱ほど、外にはみ出します。

MapLibre の `map.project()` は地面の点しか投影できないので、柱の先の位置は自分で計算しました。

```js:pages/prefmap.js（抜粋。変数名は説明用に変えています）
var f = H / 2 / Math.tan(fov / 2),        // 焦点距離(ピクセル)
  ny = H / 2 + f * Math.tan(pitch);       // カメラの真下の点が見える位置(画面の下の外)
// ...
var p = map.project([lng, lat]),
  gz = (f * f) / (f - (H / 2 - p.y) * Math.tan(pitch)),  // 地面の点の、カメラからの奥行き
  k = gz / (gz - height * ppm * Math.cos(pitch)),        // 柱の先は、真下の点から見て k 倍の位置
  tx = W / 2 + (p.x - W / 2) * k,
  ty = ny + (p.y - ny) * k;
```

計算した点を地図に重ねて、実際に描かれた柱の先と一致することを確かめてから使っています。高さは「その県の柱がいちばん高くなる産業」で見積もり、最初に1回だけ位置を決めます。産業を切り替えるたびに合わせ直すと、地図が動いてしまうからです。

## 5. 壊さないための仕組み

ページは約200、テストは85本あります（pytest ＋ Playwright。3分弱）。効いているものを挙げます。

- **数字は手で書かない。** 文章の中の数字も、すべてデータから差し込みます。
- **検算はビルドに埋める。** 県の収支、図の左右の合計、対応先のない部門。合わなければビルドが止まります。
- **テストの中で計算し直す。** 稼ぎ頭の名前と割合、産業ページの冒頭の割合は、テストがデータから計算し直して、ページの文と比べます。
- **見た目も機械で見る。** axe-core のアクセシビリティ検査を明暗の両テーマで、ラベルの重なりを狭い画面と広い画面で。
- **新しいページは、必ず幅1280pxと390pxの両方で見る。** 一度、スマホで最初の画面に何も出ないページを公開してしまい、ルールにしました。
- **公開後に、本番を確かめる。** デプロイのあと、死活監視のワークフローを手で動かして、新しいページの中身が出ているかを見ます。

- **AI は、頼んだ問いには答える。問いのほうが間違っていることは、聞かないと出てこない。** 「看板産業マップを作って」と頼めば、特化係数で地図ができます。「もう一度見つめ直したらどう思う？」と聞いて、はじめて、問いと指標が合っていないという指摘が返ってきました。
- **率直な感想は、仕様書より効く。** 「AIが作った感がすごい」のひとことが、デザインの決まりを作り直すきっかけになりました。
- **検算とテストは、AI への信頼の代わりになる。** 31県の食い違いも、4208%も、数字を突き合わせる仕組みがあったから見つかりました。

## まとめ

- 形式がバラバラな表は、**設定ファイル＋検算**でそろえる。細かい表に切り替えたら、公表されている粗い表を再現して確かめる。
- 指標を決める前に、**問いを日本語で書いて、答えの文に当てはめる**。特化係数は「偏り」であって「稼ぎ」ではありませんでした。
- 産業連関表の**需給バランスの式は、そのまま図になる**。式なので、検算もできる。
- デザインは、色を塗り替える前に、**主役をデータにする**。動かすのは、データを表すものだけ。
